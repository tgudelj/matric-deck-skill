# X-Plane input configuration

Use the [shared application input workflow](../application-inputs.md) for discovery, inventory, MATRIC mapping and acceptance. This reference covers application-specific formats and limits.

Inspect the selected installation's `Output/preferences` and its `control profiles` subfolder. The helper discovers `X-Plane Keys.prf`, `X-Plane Joystick Settings.prf`, and named `* - Keys.prf` / `* - Joysticks.prf` pairs. Confirm the profile and aircraft association in Settings; installed `.joy` device defaults are a different format and are not evidence of active assignments.


Use the user's actual installation folder, including the chosen Steam installation when applicable. Do not search unrelated installations or read general `X-Plane.prf`, Plane Maker preferences or flight logs for input discovery. Discovery recognizes the keyboard/joystick filenames listed here; explicitly selected renamed copies can also be inventoried when their content identifies the supported format. An empty profile needs a recognized filename. Have the user save current settings through their normal workflow when a file snapshot may be stale; do not edit or reset preferences, switch profiles or operate controls to discover them.

The reader accepts text PRF files with an `I` or `A` marker and numeric `version` header, retaining that header as format metadata rather than treating it as the simulator version or proof of the source operating system. It handles this subset:

- Keyboard lines contain a key token, modifier token and exact command path. Preserve alternatives as separate rows, including aircraft/plugin command paths outside `sim/`. Letters, digits, F1-F24, known navigation keys and `Numpad-0` through `Numpad-9` can produce Windows `ActionHotkey` candidates; `<none>`, `CTRL`, `SHIFT`, `ALT` and their `+` combinations are recognized modifiers. Punctuation, numeric `KEY...` tokens, `OPT`/`CMD`, unfamiliar modifiers and unsupported keys remain unresolved. Confirm keyboard layout and target behavior; X-Plane SDK virtual codes must not be copied directly into Windows key codes.
- Joystick `_joy_BUTN_use<index>` records retain exact command paths and raw global indices. `sim/none/none` and empty button assignments are unbound. `_joy_AXIS_use<index>` records retain numeric functions; `0` is unbound. Axis rows use helper identifiers such as `axis-use:11`, **not** invented X-Plane command paths or a promise that function 11 means the same thing in every build. Verify the actual function in Settings before using it for a deck control.
- Each row retains its source line number and raw text. Other joystick preference records, including identity, calibration, reversal and response curves, remain verbatim in the profile's `preferences` list; they are not applied automatically to a candidate. Unsupported or malformed assignment lines remain in `unparsed_lines`, with warnings. Inspect both lists before claiming coverage. The reader does not resolve aircraft associations, merge global/named preferences, interpret every joystick extension or load plugin command catalogs.

All joystick rows use `device: "xplane-joystick"` as a **report namespace**, not a discovered physical-device identity. A vJoy candidate requires an explicit device map under that key, mapping an exact raw token such as `_joy_BUTN_use160` to a confirmed vJoy input. Never derive vJoy DeviceId, button number, POV direction or HID axis from an X-Plane global index or assume a physical controller can be impersonated. A mapped inventory accepts only one joystick profile; the namespace does not distinguish devices across differing saved profiles. Keyboard profiles can accompany it. Check axis direction/ranges against the preserved configuration and the game's response.

The [X-Plane manual's profile workflow](https://www.x-plane.com/manuals/desktop/#joystickandkeyboardprofiles) explains active selection and aircraft associations. Laminar's [`.joy` specification](https://developer.x-plane.com/article/creating-joystick-configuration-joy-files/) documents device defaults and platform-dependent indexing; this helper does not parse those defaults. The SDK's [key definitions](https://developer.x-plane.com/sdk/XPLMDefs/) explain why X-Plane virtual key codes are not interchangeable with Windows codes. Third-party aircraft/plugin commands require the matching aircraft/plugin to be loaded; a saved command path does not establish availability or hold/repeat semantics.


PRF syntax evidence also includes the original [keyboard reader](https://github.com/jlgabriel/StreamDeck-Profile-Generator/blob/master/app/readers/xplane_prf.py) and [FlyWithLua assignment example](https://github.com/X-Friese/FlyWithLua/blob/master/FlyWithLua/Scripts%20%28disabled%29/XPLMFindCommand_Test.lua).
